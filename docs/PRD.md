## 1. プロダクト概要

### 1.1 ビジョン
**「行きたい」を、迷わず引き出せる。**
おでかけのたびに「あの場所どこに保存したっけ？」を消し去り、行きたい場所リストの作成・閲覧・取り出しが最も気持ちよくできるマップアプリを目指す。

### 1.2 プロダクト名
**polaris** — 北極星のように、行きたい場所への道標になるアプリ。

### 1.3 一行説明
行きたい場所・お気に入りスポットを、フォルダとリストで整理し、マップ上で自在に絞り込めるおでかけアプリ。

---

## 2. 解くべき課題

Google Maps の保存機能は世界中の場所を扱えるが、「行きたい場所をしまっておく道具」としては以下の不満がある。

| # | 課題 | 結果として起きる困りごと |
|---|---|---|
| P1 | 保存したスポットをフォルダ・カテゴリ・地域で多面的に整理できない | 保存したこと自体を忘れる、思い出せても探し出せない |
| P2 | リストの作成・閲覧・編集が一級市民ではない (UIの奥にある) | 整理が後回しになり、保存リストが事実上の墓場になる |
| P3 | マップ上で「いま見たい保存スポットだけ」を絞り込めない | 旅先・デート中に該当スポットを取り出せない |

polaris は、この 3 つを正面から解決することにフォーカスする。

---

## 3. ターゲットユーザー

### 3.1 ペルソナ

**P1: ソロおでかけ派**
- 普段から気になる店・カフェ・観光地をストックする習慣がある
- 保存件数は数十〜数百件規模
- 「最近保存したのに行けてない場所」「未訪問の場所」を見たい

**P2: プランナー**
- 友達/家族/恋人と週末や旅行のおでかけプランを立てる
- 候補を出し合って、その日のルートを決めたい
- 訪問後は「行ったよ」を残してまた振り返りたい

**P3: 旅行好き**
- 数ヶ月先の旅行のために少しずつスポットを集める
- 地域 (国・都市) ごとに整理したい
- 現地では「いま近くの保存済み」を取り出したい

### 3.2 主な利用シーン
1. **平時のストック**: SNS や記事で見つけた場所を、フォルダ内のリストに保存する。
2. **おでかけ前の選定**: リストとマップを行き来しながら、今日行く場所を決める。
3. **現地での参照**: マップ上で絞り込み (リスト・カテゴリ・地域・訪問状態)、いま近い候補を即座に出す。
4. **複数人での候補出し**: 共有リストに各自スポットを追加し合う (Phase 2)。
5. **訪問後の記録**: 訪問のたびに所感メモ・写真を残し、訪問履歴として蓄積する。

## 4. 価値仮説と差別化

### 4.1 ユーザーが感じる価値
- 「保存した記憶があるあの店」が **3 タップ以内で出てくる**
- 「今日行ける範囲のカフェ候補」が **マップ上で一望できる**
- リスト整理が **重くない・楽しい** ので続けられる

### 4.2 vs Google Maps
| 観点 | Google Maps | polaris |
|---|---|---|
| リスト数 | 実質ハードリミットあり、分類が浅い | フォルダ → リストの 2 階層で多面整理 |
| マップ絞り込み | 全保存表示 or リスト単位のみ | リスト・自動カテゴリ・地域・訪問状態・複数条件で絞り込み |
| 編集動線 | 詳細画面の奥 | リスト/マップから 1 タップで開ける編集ビュー |
| 訪問記録 | チェックイン文化が薄い | 訪問履歴 (複数回) ・所感・写真を一級市民に |
| 共有 | リスト単位で可、編集権限の粒度は粗い | 共有リスト + 個別ピンの編集ロック (Phase 2) |

### 4.3 やらないこと (Out of Scope)
- 経路探索・ナビゲーション (Google Maps に任せる)
- 飲食店予約・チケット購入 (連携リンクに留める)
- SNS 的なフォロー/タイムライン機能

## 5. MVP スコープ (Phase 1)

> **MVP の合言葉: 「ソロでフル機能、共有はあとで」**
> Phase 1 は単独ユーザーの「保存→整理→引き出し」の体験を完成させ、Phase 2 で共有を載せる。

### 5.1 機能要件 (Must Have)

#### F1. スポット検索・追加
- Google Places API (New) でテキスト検索・現在地周辺検索
- 検索結果の詳細 (写真・住所・営業時間・評価) を表示
- 1 タップでリストに保存。**複数リストへの同時保存可**
- 保存時に **自動カテゴリ判定** (Places types から `food / entertainment / sightseeing / shopping / lodging / other`) と **地域自動導出** (`prefecture` / `city`) を実施
- Places データは **30 日経過で自動再取得** (詳細は DATA_MODEL.md §6)

#### F2. フォルダ・リスト管理 (2 階層)
- **フォルダ**: 最上位の整理単位 (例: 「東京」「京都旅行 2026」「デート候補」)
- **リスト**: フォルダ配下のリスト (例: 「カフェ」「ラーメン」「観光」)
- フォルダ・リストごとにアイコン・カラー・カバー写真
- リスト内の並び替え (手動・追加日・距離・名前)
- ユーザーが付ける**タグ機能はなし** (整理はフォルダ・リストで完結)

#### F3. 自動カテゴリによる絞り込み
- 各スポットには Places types から自動付与された `primary_category` が入る
- ユーザーは「食べ物だけ」「観光だけ」などをワンタップでフィルタ可能
- 「フォトジェニック」「デート向き」などの soft attribute は Phase 2 で LLM 推論で導入予定

#### F4. マップ上の絞り込み
- 表示対象を **リスト・自動カテゴリ・地域 (都道府県/市区町村)・訪問状態** でフィルタ
- 複数条件の AND/OR 切り替え
- 「現在地から N km 以内の保存済み」の即時表示
- ピン色をリスト or カテゴリで切り替え

#### F5. 高速なリスト閲覧・編集
- マップとリストの 2 ペイン (スマホはボトムシート切替)
- スワイプでリスト間移動・訪問記録追加・「行きたい」トグル
- 一括編集 (複数選択 → リスト追加 / 移動 / 削除)

#### F6. 訪問履歴管理 (1:N)
- スポットに **複数の訪問記録** を残せる (例: 同じカフェに 3 回行った履歴)
- 各訪問に: 日時 / 所感メモ / 評価 (1-5) / 同行者 / 金額 / 写真
- スポット単位の状態は派生表示: `未訪問 / 訪問済み (回数)` + `行きたい` フラグ (独立、訪問後でも立てられる)
- 「最近行った」「ずっと未訪問」のスマートビュー

#### F7. ローカル永続化と同期準備
- オフライン閲覧可能 (端末ローカル DB)
- 後続の共有機能のため、全エンティティに UUIDv7 + `updatedAt` + `deletedAt` を保持

### 5.2 非機能要件
- **プラットフォーム**: iOS 16+ / Android 10+ (Flutter)
- **オフライン**: 検索以外の全機能はオフラインで完結
- **パフォーマンス**: 1,000 スポット保存時もマップ描画 60fps を目標
- **アクセシビリティ**: 主要操作は片手・ボトムシート優先
- **プライバシー**: 訪問履歴・現在地は外部送信しない (Phase 1)

### 5.3 技術スタック
詳細は [TECH_STACK.md](./TECH_STACK.md)、データモデルは [DATA_MODEL.md](./DATA_MODEL.md)、AI 実装規約は [CLAUDE.md](../CLAUDE.md) 参照。

確定済みの主要選定:
- **アプリ**: Flutter / Dart 3.x
- **状態管理**: Riverpod 2.x (codegen)
- **ローカル DB**: Drift (SQLite)
- **マップ**: `google_maps_flutter` (薄ラッパで隠蔽)
- **検索**: Google Places API (New) + dio + 自前キャッシュ
- **認証/バックエンド**: Phase 1 はなし。Phase 2 で選定

## 6. Phase 2 以降の展望

### Phase 2: 共有とコラボレーション
- アカウント (Apple / Google サインイン)
- 共有リスト (招待 URL、編集 / 閲覧権限)
- 共有リストでの追加通知、コメント

### Phase 3: プランニング
- 1 日のルート組み立て (リスト → 順序付き訪問プラン)
- 移動時間・営業時間を踏まえた候補時刻の提案
- Google Maps へのルート連携 (経路探索は外部に投げる)

### Phase 4: 発見
- 共有リストの公開 (例: 「恵比寿カフェ 30 選」のシェア)
- フォローではなく「リストを保存」する設計

## 8. リスクとオープンクエスチョン

### 8.1 リスク
- **R1: Google Places API のコスト** — 検索リクエスト課金。キャッシュ戦略を Phase 1 内で設計する必要。
- **R2: Google Maps 利用規約** — 保存スポットを長期キャッシュ・他社マップで再利用する場合の規約確認。
- **R3: 他者からのスポットインポート要望** — Google Takeout からのインポート期待が出る可能性。MVP では非対応とするが将来検討。

### 8.2 オープンクエスチョン
- ✅ Q1: マップ抽象化 → **L1 薄ラッパ** で確定 (TECH_STACK.md §2.4)
- ✅ Q2: タグ vs 地域 → **タグ廃止**、地域は緯度経度から自動導出で確定 (DATA_MODEL.md §0)
- ✅ Q3: 訪問写真 → **端末ローカル**で確定 (Phase 1)
- Q4: アプリ名 `polaris` の商標・既存アプリ衝突確認 — 未調査
