# polaris-app PRD

> ステータス: Draft v0.1 / 最終更新: 2026-05-10

## 1. プロダクト概要

### 1.1 ビジョン
**「行きたい」を、迷わず引き出せる。**
おでかけのたびに「あの場所どこに保存したっけ？」を消し去り、行きたい場所リストの作成・閲覧・取り出しが最も気持ちよくできるマップアプリを目指す。

### 1.2 プロダクト名
**polaris** — 北極星のように、行きたい場所への道標になるアプリ。

### 1.3 一行説明
行きたい場所・お気に入りスポットを、リストとタグで整理し、マップ上で自在に絞り込めるおでかけアプリ。

---

## 2. 解くべき課題

Google Maps の保存機能は世界中の場所を扱えるが、「行きたい場所をしまっておく道具」としては以下の不満がある。

| # | 課題 | 結果として起きる困りごと |
|---|---|---|
| P1 | 保存したスポットをカテゴリ・フォルダ・地域で多面的に分類できない | 保存したこと自体を忘れる、思い出せても探し出せない |
| P2 | リストの作成・閲覧・編集が一級市民ではない (UIの奥にある) | 整理が後回しになり、保存リストが事実上の墓場になる |
| P3 | マップ上で「いま見たい保存スポットだけ」を絞り込めない | 旅先・デート中に該当スポットを取り出せない |

polaris は、この 3 つを正面から解決することにフォーカスする。

---

## 3. ターゲットユーザー

### 3.1 ペルソナ

**P1: ソロおでかけ派**
- 普段から気になる店・カフェ・観光地をストックする習慣がある
- 保存件数は数十〜数百件規模
- 「最近保存したのに行けてない場所」「未訪問の場所」を見たい

**P2: プランナー**
- 友達/家族/恋人と週末や旅行のおでかけプランを立てる
- 候補を出し合って、その日のルートを決めたい
- 訪問後は「行ったよ」を残してまた振り返りたい

**P3: 旅行好き**
- 数ヶ月先の旅行のために少しずつスポットを集める
- 地域 (国・都市) ごとに整理したい
- 現地では「いま近くの保存済み」を取り出したい

### 3.2 主な利用シーン
1. **平時のストック**: SNS や記事で見つけた場所を、リスト + タグで保存する。
2. **おでかけ前の選定**: リストとマップを行き来しながら、今日行く場所を決める。
3. **現地での参照**: マップ上で絞り込み、いま近い候補を即座に出す。
4. **複数人での候補出し**: 共有リストに各自スポットを追加し合う (Phase 2)。
5. **訪問後の記録**: 訪問済みフラグ・所感メモ・写真を残す。

## 4. 価値仮説と差別化

### 4.1 ユーザーが感じる価値
- 「保存した記憶があるあの店」が **3 タップ以内で出てくる**
- 「今日行ける範囲のカフェ候補」が **マップ上で一望できる**
- リスト整理が **重くない・楽しい** ので続けられる

### 4.2 vs Google Maps
| 観点 | Google Maps | polaris |
|---|---|---|
| リスト数 | 実質ハードリミットあり、分類が浅い | 階層タグ + 複数リストで多面整理 |
| マップ絞り込み | 全保存表示 or リスト単位のみ | タグ・地域・訪問状態・複数条件で絞り込み |
| 編集動線 | 詳細画面の奥 | リスト/マップから 1 タップで開ける編集ビュー |
| 訪問記録 | チェックイン文化が薄い | 訪問済み/未訪問・所感・写真を一級市民に |
| 共有 | リスト単位で可、編集権限の粒度は粗い | 共有リスト + 個別ピンの編集ロック (Phase 2) |

### 4.3 やらないこと (Out of Scope)
- 経路探索・ナビゲーション (Google Maps に任せる)
- 飲食店予約・チケット購入 (連携リンクに留める)
- SNS 的なフォロー/タイムライン機能

## 5. MVP スコープ (Phase 1)

> **MVP の合言葉: 「ソロでフル機能、共有はあとで」**
> Phase 1 は単独ユーザーの「保存→整理→引き出し」の体験を完成させ、Phase 2 で共有を載せる。

### 5.1 機能要件 (Must Have)

#### F1. スポット検索・追加
- Google Places API でテキスト検索・現在地周辺検索
- 検索結果の詳細 (写真・住所・営業時間・評価) を表示
- 1 タップでリストに保存。複数リストへの同時保存可

#### F2. リスト管理
- 複数リストの作成 (例: 「行きたいカフェ」「東京デート」「京都旅行 2026」)
- リストごとにアイコン・カラー・カバー写真
- リスト内の並び替え (手動・追加日・距離・名前)

#### F3. 階層タグ
- スポットに複数タグ付与 (例: `#カフェ` `#休日OK` `#東京/恵比寿`)
- タグは階層構造を許容 (`地域/東京/恵比寿`)
- タグの一括リネーム・統合

#### F4. マップ上の絞り込み
- 表示対象のリスト/タグ/訪問状態をフィルタ
- 複数条件の AND/OR 切り替え
- 「現在地から N km 以内の保存済み」の即時表示
- ピン色をリスト or タグで切り替え

#### F5. 高速なリスト閲覧・編集
- マップとリストの 2 ペイン (スマホはボトムシート切替)
- スワイプでリスト間移動・タグ追加・訪問済みトグル
- 一括編集 (複数選択 → タグ付与 / 移動 / 削除)

#### F6. 訪問済み管理
- 各スポットに `未訪問 / 行きたい / 訪問済み` 状態
- 訪問日・所感メモ・写真 (端末ローカル) を残せる
- 「最近行った」「ずっと未訪問」のスマートビュー

#### F7. ローカル永続化と同期準備
- オフライン閲覧可能 (端末ローカル DB)
- 後続の共有機能のため、データモデルは同期可能な形 (UUID + 更新時刻) を最初から採用

### 5.2 非機能要件
- **プラットフォーム**: iOS 16+ / Android 10+ (Flutter)
- **オフライン**: 検索以外の全機能はオフラインで完結
- **パフォーマンス**: 1,000 スポット保存時もマップ描画 60fps を目標
- **アクセシビリティ**: 主要操作は片手・ボトムシート優先
- **プライバシー**: 訪問履歴・現在地は外部送信しない (Phase 1)

### 5.3 技術スタック (現時点の前提)
- **アプリ**: Flutter (Dart)
- **マップ**: `google_maps_flutter` + Google Maps Platform
- **検索**: Google Places API (New)
- **ローカル DB**: 候補 — Isar / Drift / sqflite (Phase 1 内で決定)
- **状態管理**: 候補 — Riverpod (有力)
- **バックエンド**: Phase 1 はなし。Phase 2 で Firebase or 自前 API を検討

## 6. Phase 2 以降の展望

### Phase 2: 共有とコラボレーション
- アカウント (Apple / Google サインイン)
- 共有リスト (招待 URL、編集 / 閲覧権限)
- 共有リストでの追加通知、コメント

### Phase 3: プランニング
- 1 日のルート組み立て (リスト → 順序付き訪問プラン)
- 移動時間・営業時間を踏まえた候補時刻の提案
- Google Maps へのルート連携 (経路探索は外部に投げる)

### Phase 4: 発見
- 共有リストの公開 (例: 「恵比寿カフェ 30 選」のシェア)
- フォローではなく「リストを保存」する設計

## 8. リスクとオープンクエスチョン

### 8.1 リスク
- **R1: Google Places API のコスト** — 検索リクエスト課金。キャッシュ戦略を Phase 1 内で設計する必要。
- **R2: Google Maps 利用規約** — 保存スポットを長期キャッシュ・他社マップで再利用する場合の規約確認。
- **R3: 他者からのスポットインポート要望** — Google Takeout からのインポート期待が出る可能性。MVP では非対応とするが将来検討。

### 8.2 オープンクエスチョン
- Q1: マップ表示は Google Maps 一択にするか、将来 Mapbox / Apple Maps に切り替え可能な抽象化を最初から入れるか
- Q2: 階層タグと「地域」概念は別物 (タグは自由、地域は緯度経度から自動付与) として扱うべきか、タグに統合するか
- Q3: 訪問済みの「写真」はクラウド保存するか端末ローカル限定か (Phase 1 はローカル想定)
- Q4: アプリ名 `polaris` の商標・既存アプリ衝突確認
