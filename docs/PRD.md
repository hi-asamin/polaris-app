## 1. プロダクト概要

### 1.1 ビジョン
**「行きたい」を、迷わず引き出せる。**
おでかけのたびに「あの場所どこに保存したっけ？」を消し去り、行きたい場所リストの作成・閲覧・取り出しが最も気持ちよくできるマップアプリを目指す。

### 1.2 プロダクト名
**polaris** — 北極星のように、行きたい場所への道標になるアプリ。

### 1.3 一行説明
行きたい場所・お気に入りスポットをフォルダで整理し、マップ上で自在に絞り込めるおでかけアプリ。

---

## 2. 解くべき課題

Google Maps の保存機能は世界中の場所を扱えるが、「行きたい場所をしまっておく道具」としては以下の不満がある。

| # | 課題 | 結果として起きる困りごと |
|---|---|---|
| P1 | 保存したスポットをフォルダ・カテゴリ・地域で多面的に整理できない | 保存したこと自体を忘れる、思い出せても探し出せない |
| P2 | フォルダの作成・閲覧・編集が一級市民ではない (UIの奥にある) | 整理が後回しになり、保存先が事実上の墓場になる |
| P3 | マップ上で「いま見たい保存スポットだけ」を絞り込めない | 旅先・デート中に該当スポットを取り出せない |
| P4 | 保存先が Google Maps だけでなく Instagram の「保存」・スクショ・SNS のシェアにも分散する | 「あの店どこに保存したっけ」がアプリ横断で発生し、取り出しコストが跳ね上がる |

polaris は、この 4 つを正面から解決することにフォーカスする。P1〜P3 を Phase 1、P4 を Phase 1.5 (§6) で扱う。

---

## 3. ターゲットユーザー

### 3.1 ペルソナ

**P1: Google Maps 破綻ユーザー (MVP プライマリ)**

> 「保存しすぎて、もう探せない」状態に達した人。polaris の MVP はこの人に振り切る。

- **行動**: SNS / 記事 / 口コミで気になった場所を Google Maps の「お気に入り」「行きたい」に保存し続けてきた
- **保存件数**: 100 件以上 (=Google Maps の保存 UI が破綻する閾値)
- **痛み (具体)**:
  - 「あのカフェ保存したはず」が思い出せても、保存先のどこにあるか辿れない
  - 「今いる渋谷の周辺で、保存済みのスポットだけ」を地図に出す手段がない
  - 保存先が「行きたい」「お気に入り」「Want to go」と用途が混ざり、整理し直す気力もない
- **未充足のジョブ**: 「保存した記憶から、今すぐ取り出すこと」
- **既存代替**: Google Maps のリスト + 検索フィルタ手動 (限界に達している) / Notion・メモアプリへの移植 (地図と切り離されて使われない)
- **獲得仮説**: 「Google Maps の保存が 100 件超えた人」を SNS で能動的に探す + Google Maps からのインポート動線が刺さる

**P2: プランナー** (Phase 2 主役 / Phase 1 ではセカンダリ)
- 友達/家族/恋人と週末や旅行のおでかけプランを立てる
- 候補を出し合って、その日のルートを決めたい
- 訪問後は「行ったよ」を残してまた振り返りたい
- **Phase 1 では一人運用に閉じるため、共有要件は Phase 2 で本格対応**

**P3: 旅行好き** (Phase 1 でも P1 と同居しうる)
- 数ヶ月先の旅行のために少しずつスポットを集める
- 地域 (国・都市) ごとに整理したい
- 現地では「いま近くの保存済み」を取り出したい
- **P1 の派生として、フォルダ=旅行先という使い方で同じ機能セットを享受できる**

### 3.2 主な利用シーン
1. **平時のストック**: SNS や記事で見つけた場所を、フォルダに保存する。
2. **おでかけ前の選定**: フォルダとマップを行き来しながら、今日行く場所を決める。
3. **現地での参照**: マップ上で絞り込み (フォルダ・カテゴリ・地域・訪問状態)、いま近い候補を即座に出す。
4. **複数人での候補出し**: 共有フォルダに各自スポットを追加し合う (Phase 2)。
5. **訪問後の記録**: 訪問のたびに所感メモ・写真を残し、訪問履歴として蓄積する。

## 4. 価値仮説と差別化

### 4.1 ユーザーが感じる価値
- 「保存した記憶があるあの店」が **3 タップ以内で出てくる**
- 「今日行ける範囲のカフェ候補」が **マップ上で一望できる**
- フォルダ整理が **重くない・楽しい** ので続けられる

### 4.2 vs Google Maps
| 観点 | Google Maps | polaris |
|---|---|---|
| 整理 | 実質ハードリミット、分類が浅い | 1 階層のフォルダで多面整理 + 「行きたい」システムフォルダで未訪問を自動集約 |
| マップ絞り込み | 全保存表示 or リスト単位のみ | フォルダ・自動カテゴリ・地域・訪問状態・複数条件で絞り込み |
| 編集動線 | 詳細画面の奥 | フォルダ/マップから 1 タップで開ける編集ビュー |
| 訪問記録 | チェックイン文化が薄い | 訪問履歴 (複数回) ・所感・写真を一級市民に |
| 共有 | リスト単位で可、編集権限の粒度は粗い | 共有フォルダ + 個別ピンの編集ロック (Phase 2) |

### 4.3 やらないこと (Out of Scope)
- 経路探索・ナビゲーション (Google Maps に任せる)
- 飲食店予約・チケット購入 (連携リンクに留める)
- SNS 的なフォロー/タイムライン機能

## 5. MVP スコープ (Phase 1)

> **MVP の合言葉: 「ソロでフル機能、共有はあとで」**
> Phase 1 は単独ユーザーの「保存→整理→引き出し」の体験を完成させ、Phase 2 で共有を載せる。

### 5.1 機能要件 (Must Have)

#### F1. スポット検索・追加
- Google Places API (New) でテキスト検索・現在地周辺検索
- 検索結果の詳細 (写真・住所・営業時間・評価) を表示
- 1 タップでフォルダに保存。**複数フォルダへの同時保存可**
- 未訪問なら **「行きたい」フォルダ (システム) にデフォルトでチェック** が入る (uncheck も可)
- 保存シート末尾から **その場で新しいフォルダを作成** できる
- 保存時に **自動カテゴリ判定** (Places types から `food / entertainment / sightseeing / shopping / lodging / other`) と **地域自動導出** (`prefecture` / `city`) を実施
- Places データは **30 日経過で自動再取得** (詳細は DATA_MODEL.md §6)

#### F2. フォルダ管理 (1 階層)
- **フォルダ** (例: 「東京」「京都旅行 2026」「デート候補」) が整理の唯一の単位
- フォルダの中にフォルダを作る入れ子は **不可** (意図的に 1 階層に限定)
- フォルダごとにアイコン・カラー・カバー写真
- フォルダ内の並び替え (手動・追加日・距離・名前)
- ユーザーが付ける **タグ機能はなし** (整理はフォルダで完結)
- **「行きたい」システムフォルダ** (削除不可)
  - 初回起動で自動作成され、リストタブの最上位に常駐
  - 未訪問スポットを保存すると自動で入る (= ライトな保存導線)
  - 該当スポットに訪問記録が入ると自動で外れる (= 行ったら「行きたい」が終わる)
  - ユーザーは手動で add/remove も可能 (再訪意欲を残せる)

#### F3. 自動カテゴリによる絞り込み
- 各スポットには Places types から自動付与された `primary_category` が入る
- ユーザーは「食べ物だけ」「観光だけ」などをワンタップでフィルタ可能
- 「フォトジェニック」「デート向き」などの soft attribute は Phase 2 で LLM 推論で導入予定

#### F4. マップ上の絞り込み
- 表示対象を **フォルダ・自動カテゴリ・地域 (都道府県/市区町村)・訪問状態** でフィルタ
- 複数条件の AND/OR 切り替え
- 「現在地から N km 以内の保存済み」の即時表示
- ピン色をフォルダ or カテゴリで切り替え
- 「行きたい」「お気に入り」の絞り込みチップも用意

#### F5. 高速なフォルダ閲覧・編集
- マップとフォルダの 2 ペイン (スマホはボトムシート切替)
- スワイプでフォルダ間移動・訪問記録追加・お気に入りトグル
- 一括編集 (複数選択 → フォルダ追加 / 移動 / 削除)

#### F6. 訪問記録 (1:N) と 2 軸の保存状態

訪問・保存・お気に入りを **意味の異なる 3 つの軸** として共存させる。
混乱を避けるため、それぞれの責務を厳密に分離する。

| 軸 | 実装 | 何を表現するか |
|---|---|---|
| **訪問記録** | `visits` テーブル (1:N) | 「過去に行った事実」。日時 / 所感メモ / 評価 / 同行者 / 金額 / 写真を持つ |
| **行きたい** | `行きたい`システムフォルダへの所属 (M:N) | 「未来の計画」。未訪問の意志。訪問で自動解除 |
| **お気に入り** | `Spot.isFavorite: bool` (独立フラグ) | 「リピートしたい / 好きな場所」。訪問の有無と無関係 |

- スポット単位の状態は派生表示: `未訪問 / 訪問済み (回数)` + `行きたい` + `お気に入り`
- 「最近行った」「ずっと未訪問」のスマートビュー
- アカウントタブで 3 タブ切替: 訪問済みアルバム / お気に入り / 全フォルダ保存

#### F7. ローカル永続化と同期準備
- オフライン閲覧可能 (端末ローカル DB)
- 後続の共有機能のため、全エンティティに UUIDv7 + `updatedAt` + `deletedAt` を保持

### 5.2 非機能要件
- **プラットフォーム**: iOS 16+ / Android 10+ (Flutter)
- **オフライン**: 検索以外の全機能はオフラインで完結
- **パフォーマンス**: 1,000 スポット保存時もマップ描画 60fps を目標
- **アクセシビリティ**: 主要操作は片手・ボトムシート優先
- **プライバシー**: 訪問履歴・現在地は外部送信しない (Phase 1)

### 5.3 オンボーディングと最初の体験 (First-Run Strategy)

> **合言葉: 「マップ絞り込み」を最初の 30 秒で見せきる。**

polaris の最大の堀は **「マップ上で複数条件で絞り込める」** こと。これは Google Maps が構造的にやらない領域であり、ここを最初に体験させなければ「ただの保存アプリ」と誤認される。

#### 5.3.1 ストアの主役 (App Store / Google Play スクリーンショット優先順位)

| 順序 | 画面 | 訴求 |
|---|---|---|
| **1 枚目** | **マップ + 複数条件で絞り込んだ状態** (例: 「東京」フォルダ × カフェカテゴリ × 未訪問) | 「保存した中から、いま見たいものだけ」 |
| 2 枚目 | フォルダ一覧 (「行きたい」+ ユーザーフォルダがフラットに並ぶ) | 「Google Maps では辿れなかった整理」 |
| 3 枚目 | スポット詳細 + 複数訪問履歴 | 「行った思い出も一緒に」 |
| 4 枚目 | 検索 → 複数フォルダに一気に保存 | 「保存も 1 タップ」 |
| 5 枚目 | フォルダ・カテゴリ別ピン色マップ | 「一望できる」 |

フォルダ管理画面 / フォルダ作成画面を 1 枚目に置かない。**最初の画面は必ずマップ + フィルタ済みの状態**。

#### 5.3.2 アプリ内オンボーディング (初回起動時)

- 起動直後はオンボーディングフローを **3 ステップ以下** に抑える
- ステップ構成 (現状実装):
  1. **Welcome 画面** (タグライン提示)
  2. **プロフィール設定** (名前 + イニシャル色)
  3. **サンプルデータ選択** (東京 / 京都 / 何も入れない)
- 完了で「行きたい」システムフォルダ + 選択サンプルが投入された状態でマップを起動
- 将来案: フィルタチップ (フォルダ / カテゴリ / 訪問状態) のハンズオン挿入、
  「Google Maps から保存した場所をインポートする」の動線追加

#### 5.3.3 First Aha! Moment の定義

- **30 秒以内**に「マップ上のピンが、フィルタ操作で減る/色が変わる」体験に到達すること
- 計測指標案: 初回起動セッションでフィルタを 1 回以上操作した率 ≥ 70%

#### 5.3.4 空っぽ問題への対策

P1 (Google Maps 破綻ユーザー) は最初の保存に到達するまで価値を感じない。これを潰すため:

- **オプション A (推奨)**: 初回起動時にサンプルデータ (デモ用フォルダ「東京」「京都」入り) を投入し、ユーザーは「いつでも消せる」ボタンで一括削除可能
- **オプション B**: Google Maps エクスポート (Google Takeout) のインポートを Phase 1.5 で投入し、これをオンボーディングの初手にする

(Phase 1 リリース時点では A、Phase 1.5 で B を追加する想定)

詳細は [TECH_STACK.md](./TECH_STACK.md)、データモデルは [DATA_MODEL.md](./DATA_MODEL.md)、AI 実装規約は [CLAUDE.md](../CLAUDE.md) 参照。

## 6. Phase 1.5 以降の展望

### Phase 1.5: 外部ソースからのスポット取り込み (差別化の核)

> 課題 §2 P4 を解く。Mapstr 等の競合が解けていない「Instagram / スクショ / URL に散在した『行きたい場所』をどう救出するか」を、抽出 → 場所特定 → 保存の 3 レイヤーで解く。

#### 6.1.1 入力ソース
- **スクリーンショット画像** (Instagram / X / メモアプリ等から共有)
- **URL / 共有シート経由** (Instagram 投稿、Google Maps リンク、食べログ等)
- **(将来)** Reels / TikTok のキャプション・音声

#### 6.1.2 処理レイヤー

| レイヤー | 役割 | 実装手段 |
|---|---|---|
| L1: 抽出 | 画像・テキストから店舗名・地域・住所候補を取り出す | 端末側 OCR (Apple Vision / ML Kit) + LLM (店名/住所/地域の抽出プロンプト) |
| **L2: 場所特定 (★差別化の核)** | 抽出した断片を実在の Place ID に紐付ける | Google Places **Text Search API** に投げる → 候補を確信度スコアでランキング → しきい値未満ならユーザーに選択 UI |
| L3: 保存 | 既存の Spot 保存フローに合流 | フォルダ選択 → 既存の `spots` テーブルへ挿入 (新テーブル不要) |

L2 が真の難所。Mapstr が Instagram の「位置タグ付き投稿」しか取り込めていないのは、ここをサボっているため。Polaris は L2 を自動化することで、Mapstr が放置している市場の空白を取りに行く。

#### 6.1.3 スコープ外 (この Phase ではやらない)
- 取り出し時のセマンティック検索 (出口側の自然言語検索は Phase 2 の soft attribute と合わせて検討)
- 動画音声からのテキスト化 (Phase 3 以降)
- インポート時の自動 LLM タグ付け (Phase 2 soft attribute と統合)

#### 6.1.4 Phase 1 との関係
- Phase 1 リリース時点では未投入。Phase 1 オンボーディング §5.3.4 オプション B (Google Takeout) と同じく「最初の保存到達」を加速する手段
- スキーマ追加なしで実装可能 (既存の Spot / SpotFolder で完結)
- Places API Text Search の呼び出しが追加されるため、§8.1 R1 のコストモデルを Phase 1.5 着手前に再評価する

### Phase 2: 共有 + 周辺機能

> Phase 2 の最優先は **read-only Web ビュー**。共同編集よりも先に出す。

- **read-only Web ビュー (最優先)**: 招待 URL を開いた非ユーザーが Web 上でマップを閲覧できる。バイラル獲得の核であり、Mapstr が過去に弱点として指摘された領域 (Web 未対応で共有体験が貧弱だった)。アカウントなしで開けるのがミソ
- アカウント (Apple / Google サインイン)
- 共有フォルダ (招待 URL、編集 / 閲覧権限)
- 共有フォルダでの追加通知、コメント
- **位置近接通知**: 保存スポット近接時の通知。「保存したのを忘れている」問題を能動的取り出しなしで解ける。背景位置情報のパーミッション UX と通知疲れ対策 (頻度制限・カテゴリ別 ON/OFF) は要設計

### Phase 2.5: AI セマンティック検索 (保存済みからの取り出し)

> Polaris の中核哲学「迷わず引き出せる」の最終形態。保存済みスポットを自然言語 + リアルタイム文脈で取り出す。「世界全体からの発見」は Phase 4 で扱う (Mapstr Matching の土俵で、後発参入のため意図的に後回し)。

#### 6.2.1 入力 (UX 想定)

自然言語クエリ例:
- 「今夜行ける、デート向きのイタリアン」
- 「雨の日に 1 人で入れる静かなカフェ」
- 「子連れで行ける、駅近の和食」

#### 6.2.2 処理レイヤー

| レイヤー | 役割 | 実装手段 |
|---|---|---|
| L1: クエリ解釈 | 自然言語から構造化条件 (カテゴリ / soft attribute / 時刻 / 場所制約) を抽出 | LLM プロンプト + JSON 出力 |
| L2: セマンティック検索 | スポットのメモ・soft_attributes・Places データを embedding 化し、ベクトル類似度で候補抽出 | ローカル embedding (端末側) or クラウド推論 (Q7 で判断) |
| L3: リアルタイム文脈統合 | 現在時刻 × 営業時間、現在地、移動可能距離、(天気) でフィルタ・スコアリング | ローカル計算 |
| L4: ランキング | 関連度 (L2) × 実用性 (L3) の合成スコアで並び替え | ローカル計算 |

#### 6.2.3 前提
- Phase 2 の soft_attributes_json (DATA_MODEL §3.2) がスポットに付与されていること
- バックエンド必須かは Q7 (§8.2) の推論場所判断による。端末側完結が可能ならバックエンド非依存で実装可

#### 6.2.4 スコープ外 (この Phase ではやらない)
- **「世界全体からの最適スポット発見」** (Mapstr Matching 相当) → Phase 4 以降
- LLM による自動メモ生成 → 将来検討
- 音声入力 → 将来検討
- クエリ履歴の永続化 → Q7 で要判断

### Phase 3: プランニング
- 1 日のルート組み立て (フォルダ → 順序付き訪問プラン)
- 移動時間・営業時間を踏まえた候補時刻の提案
- Google Maps へのルート連携 (経路探索は外部に投げる)
- 予約サービスへの**ディープリンク** (Tabelog / Hot Pepper / OpenTable 等)。**統合ではなくリンクに留める** (§4.3)。Mapstr Pro が持つ「アプリ内予約」は本プロダクトの差別化ではないため踏み込まない

### Phase 4: 発見

3 種類のキュレーションを並走させる:

1. **個人起点**: 共有フォルダの公開 (例: 「恵比寿カフェ 30 選」のシェア) / フォローではなく「フォルダを保存」する設計
2. **編集者起点**: 媒体・キュレーターとの協業 (Mapstr の mapStore 相当)。**Phase 1〜3 で取り出し体験の差別化を完成させてから着手**。先行投資すると媒体側に組む理由がない
3. **集合知起点** (スケッチ): 多ユーザーの保存・訪問データを集約した「ホットスポット」キュレーション。Foursquare の "Trending Nearby" / Google Maps の "Popular Times" に近いアルゴリズム駆動の発見体験。詳細設計は §8.2 Q6 で未決。実装は Phase 2 バックエンド + データ蓄積後 (実質 Phase 4.5 以降)

## 8. リスクとオープンクエスチョン

### 8.1 リスク
- **R1: Google Places API のコスト** — 検索リクエスト課金。キャッシュ戦略を Phase 1 内で設計する必要。**Phase 1.5 (§6.1) の外部ソースインポートで Text Search 呼び出しが追加されるため、Phase 1.5 着手前にコストモデルを再評価する**。
- **R2: Google Maps 利用規約** — 保存スポットを長期キャッシュ・他社マップで再利用する場合の規約確認。
- **R3: 他者からのスポットインポート要望** — Google Takeout からのインポート期待が出る可能性。MVP では非対応とするが将来検討 (オンボーディング戦略 §5.3.4 でも Phase 1.5 候補として言及)。
- **R4: 「polaris」名称の商標・既存アプリ衝突 (重大)** — 2026-05-17 の調査で複数の競合・先行使用を確認。**MVP コミット前にリネームの最終判断が必要**。詳細は §8.2 Q4 参照。

### 8.2 オープンクエスチョン
- ✅ Q1: マップ抽象化 → **L1 薄ラッパ** で確定 (TECH_STACK.md §2.4)
- ✅ Q2: タグ vs 地域 → **タグ廃止**、地域は緯度経度から自動導出で確定 (DATA_MODEL.md §0)
- ✅ Q3: 訪問写真 → **端末ローカル**で確定 (Phase 1)
- ⚠️ **Q5: Phase 1.5 外部ソースインポート (§6.1) の Entity Resolution 設計** (2026-05-24 追加)
  - L2 (場所特定) の確信度しきい値: いくつまで自動確定、いくつから候補選択 UI を出すか
  - Places Text Search の呼び出し頻度はユーザー体験 / コストを損ねない範囲か (R1 と連動)
  - OCR / LLM 推論を端末側で完結させるか、クラウド推論を併用するか (プライバシー §5.2 と連動)
  - スクショから店舗が一意に決まらないケース (例: チェーン店、住所が部分的) のフォールバック UX
- ⚠️ **Q7: Phase 2.5 AI セマンティック検索 (§6.2) の実装方針** (2026-05-24 追加)
  - 端末側 embedding 推論 vs クラウド推論 (プライバシー §5.2 と連動)。端末側で完結できれば Phase 2 バックエンド非依存
  - リアルタイム文脈 (現在地・時刻) を毎回サーバーに送る設計の同意フロー (端末側完結なら不要)
  - LLM が意図を取り違えたときの修正動線 (例: 「違う候補を見たい」「条件を緩めたい」)
  - クエリ履歴を端末側に保存する / しないの判断
  - 結果ゼロ件のフォールバック (条件緩和の自動提案、または「保存していないかも」の案内)
  - Places API リアルタイム情報 (営業時間・混雑) の取得頻度とコスト (R1 と連動)
- ⚠️ **Q6: Phase 4 集合知ホットスポットの設計判断** (2026-05-24 追加)
  - シグナル選択: 保存数 / 訪問数 / 行きたい数の重み付け、直近 N 日減衰
  - プライバシー: 集計値のみ・個人非特定・オプトアウト UX。§5.2「訪問履歴・現在地は外部送信しない」と直接衝突するため、Phase 2 アカウント機能と同時にユーザー同意フローを設計する必要
  - コールドスタート: ユーザー数が一定規模に達するまで媒体協業 (Phase 4 編集者起点) で穴埋めし、段階展開する
  - 地理的粒度 (都道府県 / 市区町村 / 駅周辺 / 現在地半径)
  - アンチ・ゲーミング (店舗の自作自演ブースト・Bot 対策)
  - 表示モード (発見タブ / マップオーバーレイ / 通知)
