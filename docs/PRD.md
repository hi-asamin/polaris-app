## 1. プロダクト概要

### 1.1 ビジョン
**「行きたい」を、迷わず引き出せる。**
おでかけのたびに「あの場所どこに保存したっけ？」を消し去り、行きたい場所リストの作成・閲覧・取り出しが最も気持ちよくできるマップアプリを目指す。

### 1.2 プロダクト名
**polaris** — 北極星のように、行きたい場所への道標になるアプリ。

### 1.3 一行説明
行きたい場所・お気に入りスポットを、フォルダとリストで整理し、マップ上で自在に絞り込めるおでかけアプリ。

---

## 2. 解くべき課題

Google Maps の保存機能は世界中の場所を扱えるが、「行きたい場所をしまっておく道具」としては以下の不満がある。

| # | 課題 | 結果として起きる困りごと |
|---|---|---|
| P1 | 保存したスポットをフォルダ・カテゴリ・地域で多面的に整理できない | 保存したこと自体を忘れる、思い出せても探し出せない |
| P2 | リストの作成・閲覧・編集が一級市民ではない (UIの奥にある) | 整理が後回しになり、保存リストが事実上の墓場になる |
| P3 | マップ上で「いま見たい保存スポットだけ」を絞り込めない | 旅先・デート中に該当スポットを取り出せない |

polaris は、この 3 つを正面から解決することにフォーカスする。

## 3. ターゲットユーザー

### 3.1 ペルソナ

**P1: Google Maps 破綻ユーザー (MVP プライマリ)**

> 「保存しすぎて、もう探せない」状態に達した人。polaris の MVP はこの人に振り切る。

- **行動**: SNS / 記事 / 口コミで気になった場所を Google Maps の「お気に入り」「行きたい」に保存し続けてきた
- **保存件数**: 100 件以上 (=Google Maps のリスト UI が破綻する閾値)
- **痛み (具体)**:
  - 「あのカフェ保存したはず」が思い出せても、リスト内のどこにあるか辿れない
  - 「今いる渋谷の周辺で、保存済みのスポットだけ」を地図に出す手段がない
  - リストが「行きたい」「お気に入り」「Want to go」と用途が混ざり、整理し直す気力もない
- **未充足のジョブ**: 「保存した記憶から、今すぐ取り出すこと」
- **既存代替**: Google Maps のリスト + 検索フィルタ手動 (限界に達している) / Notion・メモアプリへの移植 (地図と切り離されて使われない)
- **獲得仮説**: 「Google Maps の保存が 100 件超えた人」を SNS で能動的に探す + Google Maps からのインポート動線が刺さる

**P2: プランナー** (Phase 2 主役 / Phase 1 ではセカンダリ)
- 友達/家族/恋人と週末や旅行のおでかけプランを立てる
- 候補を出し合って、その日のルートを決めたい
- 訪問後は「行ったよ」を残してまた振り返りたい
- **Phase 1 では一人運用に閉じるため、共有要件は Phase 2 で本格対応**

**P3: 旅行好き** (Phase 1 でも P1 と同居しうる)
- 数ヶ月先の旅行のために少しずつスポットを集める
- 地域 (国・都市) ごとに整理したい
- 現地では「いま近くの保存済み」を取り出したい
- **P1 の派生として、フォルダ=旅行先という使い方で同じ機能セットを享受できる**

### 3.2 主な利用シーン
1. **平時のストック**: SNS や記事で見つけた場所を、フォルダ内のリストに保存する。
2. **おでかけ前の選定**: リストとマップを行き来しながら、今日行く場所を決める。
3. **現地での参照**: マップ上で絞り込み (リスト・カテゴリ・地域・訪問状態)、いま近い候補を即座に出す。
4. **複数人での候補出し**: 共有リストに各自スポットを追加し合う (Phase 2)。
5. **訪問後の記録**: 訪問のたびに所感メモ・写真を残し、訪問履歴として蓄積する。

## 4. 価値仮説と差別化

### 4.1 ユーザーが感じる価値
- 「保存した記憶があるあの店」が **3 タップ以内で出てくる**
- 「今日行ける範囲のカフェ候補」が **マップ上で一望できる**
- リスト整理が **重くない・楽しい** ので続けられる

### 4.2 vs Google Maps
| 観点 | Google Maps | polaris |
|---|---|---|
| リスト数 | 実質ハードリミットあり、分類が浅い | フォルダ → リストの 2 階層で多面整理 |
| マップ絞り込み | 全保存表示 or リスト単位のみ | リスト・自動カテゴリ・地域・訪問状態・複数条件で絞り込み |
| 編集動線 | 詳細画面の奥 | リスト/マップから 1 タップで開ける編集ビュー |
| 訪問記録 | チェックイン文化が薄い | 訪問履歴 (複数回) ・所感・写真を一級市民に |
| 共有 | リスト単位で可、編集権限の粒度は粗い | 共有リスト + 個別ピンの編集ロック (Phase 2) |

### 4.3 やらないこと (Out of Scope)
- 経路探索・ナビゲーション (Google Maps に任せる)
- 飲食店予約・チケット購入 (連携リンクに留める)
- SNS 的なフォロー/タイムライン機能

## 5. MVP スコープ (Phase 1)

> **MVP の合言葉: 「ソロでフル機能、共有はあとで」**
> Phase 1 は単独ユーザーの「保存→整理→引き出し」の体験を完成させ、Phase 2 で共有を載せる。

### 5.1 機能要件 (Must Have)

#### F1. スポット検索・追加
- Google Places API (New) でテキスト検索・現在地周辺検索
- 検索結果の詳細 (写真・住所・営業時間・評価) を表示
- 1 タップでリストに保存。**複数リストへの同時保存可**
- 保存時に **自動カテゴリ判定** (Places types から `food / entertainment / sightseeing / shopping / lodging / other`) と **地域自動導出** (`prefecture` / `city`) を実施
- Places データは **30 日経過で自動再取得** (詳細は DATA_MODEL.md §6)

#### F2. フォルダ・リスト管理 (2 階層)
- **フォルダ**: 最上位の整理単位 (例: 「東京」「京都旅行 2026」「デート候補」)
- **リスト**: フォルダ配下のリスト (例: 「カフェ」「ラーメン」「観光」)
- フォルダ・リストごとにアイコン・カラー・カバー写真
- リスト内の並び替え (手動・追加日・距離・名前)
- ユーザーが付ける**タグ機能はなし** (整理はフォルダ・リストで完結)

#### F3. 自動カテゴリによる絞り込み
- 各スポットには Places types から自動付与された `primary_category` が入る
- ユーザーは「食べ物だけ」「観光だけ」などをワンタップでフィルタ可能
- 「フォトジェニック」「デート向き」などの soft attribute は Phase 2 で LLM 推論で導入予定

#### F4. マップ上の絞り込み
- 表示対象を **リスト・自動カテゴリ・地域 (都道府県/市区町村)・訪問状態** でフィルタ
- 複数条件の AND/OR 切り替え
- 「現在地から N km 以内の保存済み」の即時表示
- ピン色をリスト or カテゴリで切り替え

#### F5. 高速なリスト閲覧・編集
- マップとリストの 2 ペイン (スマホはボトムシート切替)
- スワイプでリスト間移動・訪問記録追加・「行きたい」トグル
- 一括編集 (複数選択 → リスト追加 / 移動 / 削除)

#### F6. 訪問履歴管理 (1:N)
- スポットに **複数の訪問記録** を残せる (例: 同じカフェに 3 回行った履歴)
- 各訪問に: 日時 / 所感メモ / 評価 (1-5) / 同行者 / 金額 / 写真
- スポット単位の状態は派生表示: `未訪問 / 訪問済み (回数)` + `行きたい` フラグ (独立、訪問後でも立てられる)
- 「最近行った」「ずっと未訪問」のスマートビュー

#### F7. ローカル永続化と同期準備
- オフライン閲覧可能 (端末ローカル DB)
- 後続の共有機能のため、全エンティティに UUIDv7 + `updatedAt` + `deletedAt` を保持

### 5.2 非機能要件
- **プラットフォーム**: iOS 16+ / Android 10+ (Flutter)
- **オフライン**: 検索以外の全機能はオフラインで完結
- **パフォーマンス**: 1,000 スポット保存時もマップ描画 60fps を目標
- **アクセシビリティ**: 主要操作は片手・ボトムシート優先
- **プライバシー**: 訪問履歴・現在地は外部送信しない (Phase 1)

### 5.3 オンボーディングと最初の体験 (First-Run Strategy)

> **合言葉: 「マップ絞り込み」を最初の 30 秒で見せきる。**

polaris の最大の堀は **「マップ上で複数条件で絞り込める」** こと。これは Google Maps が構造的にやらない領域であり、ここを最初に体験させなければ「ただの保存アプリ」と誤認される。

#### 5.3.1 ストアの主役 (App Store / Google Play スクリーンショット優先順位)

| 順序 | 画面 | 訴求 |
|---|---|---|
| **1 枚目** | **マップ + 複数条件で絞り込んだ状態** (例: 「東京」フォルダ × カフェカテゴリ × 未訪問) | 「保存した中から、いま見たいものだけ」 |
| 2 枚目 | フォルダ → リストの 2 階層整理ビュー | 「Google Maps では辿れなかった整理」 |
| 3 枚目 | スポット詳細 + 複数訪問履歴 | 「行った思い出も一緒に」 |
| 4 枚目 | 検索 → 複数リストに一気に保存 | 「保存も 1 タップ」 |
| 5 枚目 | リスト・カテゴリ別ピン色マップ | 「一望できる」 |

リスト管理画面 / フォルダ作成画面を 1 枚目に置かない。**最初の画面は必ずマップ + フィルタ済みの状態**。

#### 5.3.2 アプリ内オンボーディング (初回起動時)

- 起動直後はオンボーディングフローを **3 ステップ以下** に抑える
- ステップ構成 (案):
  1. **サンプルデータで埋まったマップ画面**を即見せる (空っぽのマップは見せない)
  2. フィルタチップ (リスト / カテゴリ / 訪問状態) のタップを促す **1 アクションだけ**のハンズオン
  3. 「Google Maps から保存した場所をインポートする」 or 「最初の場所を検索して保存する」の二択
- **チュートリアル文章で説明しない**。フィルタを押すと「絞り込まれる挙動」を体験させる。

#### 5.3.3 First Aha! Moment の定義

- **30 秒以内**に「マップ上のピンが、フィルタ操作で減る/色が変わる」体験に到達すること
- 計測指標案: 初回起動セッションでフィルタを 1 回以上操作した率 ≥ 70%

#### 5.3.4 空っぽ問題への対策

P1 (Google Maps 破綻ユーザー) は最初の保存に到達するまで価値を感じない。これを潰すため:

- **オプション A (推奨)**: 初回起動時にサンプルデータ (デモ用フォルダ「東京」「京都」入り) を投入し、ユーザーは「いつでも消せる」ボタンで一括削除可能
- **オプション B**: Google Maps エクスポート (Google Takeout) のインポートを Phase 1.5 で投入し、これをオンボーディングの初手にする

(Phase 1 リリース時点では A、Phase 1.5 で B を追加する想定)

### 5.4 技術スタック
詳細は [TECH_STACK.md](./TECH_STACK.md)、データモデルは [DATA_MODEL.md](./DATA_MODEL.md)、AI 実装規約は [CLAUDE.md](../CLAUDE.md) 参照。

確定済みの主要選定:
- **アプリ**: Flutter / Dart 3.x
- **状態管理**: Riverpod 2.x (codegen)
- **ローカル DB**: Drift (SQLite)
- **マップ**: `google_maps_flutter` (薄ラッパで隠蔽)
- **検索**: Google Places API (New) + dio + 自前キャッシュ
- **認証/バックエンド**: Phase 1 はなし。Phase 2 で選定

## 8. リスクとオープンクエスチョン

### 8.1 リスク
- **R1: Google Places API のコスト** — 検索リクエスト課金。キャッシュ戦略を Phase 1 内で設計する必要。
- **R2: Google Maps 利用規約** — 保存スポットを長期キャッシュ・他社マップで再利用する場合の規約確認。
- **R3: 他者からのスポットインポート要望** — Google Takeout からのインポート期待が出る可能性。MVP では非対応とするが将来検討 (オンボーディング戦略 §5.3.4 でも Phase 1.5 候補として言及)。
- **R4: 「polaris」名称の商標・既存アプリ衝突 (重大)** — 2026-05-17 の調査で複数の競合・先行使用を確認。**MVP コミット前にリネームの最終判断が必要**。詳細は §8.2 Q4 参照。

### 8.2 オープンクエスチョン
- ✅ Q1: マップ抽象化 → **L1 薄ラッパ** で確定 (TECH_STACK.md §2.4)
- ✅ Q2: タグ vs 地域 → **タグ廃止**、地域は緯度経度から自動導出で確定 (DATA_MODEL.md §0)
- ✅ Q3: 訪問写真 → **端末ローカル**で確定 (Phase 1)
- ⚠️ **Q4: アプリ名 `polaris` の商標・既存アプリ衝突 — 調査完了、リネーム推奨** (2026-05-17)

  **発見した主要衝突 (要約)**:

  | 衝突先 | 提供元 | 内容 | 影響度 |
  |---|---|---|---|
  | **Polaris® App** (App Store ID 493558794) | Polaris Industries Inc. (米上場企業) | オフロード車両向けマップ・ウェイポイント・ルート保存アプリ。`POLARIS` は登録商標 (米) | **最大**: App Store の "Polaris" 検索 1 位を占有。商標侵害リスクあり |
  | **Polaris (ロードマップ管理アプリ)** | 株式会社レベルアップ (日本) | 日本のタスク管理アプリ。**ドメイン `polaris-app.jp` を取得済み** | **大**: 日本市場で名称・ドメインともに完全衝突 |
  | **Polaris Office Mobile** (App Store ID 513188658) | Polaris Office Corp. | 文書編集アプリ。App Store 検索結果上位 | 中: ジャンルは違うが SEO 汚染 |
  | **Polaris GPS Hike, Bike, Marine** | Discipleskies (Android) | GPS ナビアプリ。**カテゴリ近接** | 中 |
  | **Polaris (ポラリス)** 占い記録 (App Store ID 1545951536) | — | 日本のアプリ。日本語で "ポラリス" として App Store に存在 | 小 |
  | **Shopify Polaris** | Shopify | デザインシステム名。検索結果汚染要因 | 小 (SEO) |

  **付随する未解決調査**:
  - 日本の商標公報 (J-PlatPat) で「ポラリス」「POLARIS」の第 9 類 / 第 42 類の登録状況を弁理士に依頼して確認すること
  - US PTO で `POLARIS` の登録範囲 (IC 9 / IC 42) を確認すること

  **判断**: **Phase 1 リリース前にリネーム**を強く推奨。理由:
  1. App Store / Google Play で "polaris" 検索しても発見されない (Polaris Industries が上位独占)
  2. 国内ドメインの第一候補 `polaris-app.jp` がすでに使われている (本リポジトリのディレクトリ名と同一)
  3. Polaris Industries が地図系機能を含むアプリを展開しているため、商標侵害クレームの可能性が無視できない

  **次アクション**: リネーム候補のブレストを別途実施し、本 PRD を更新する。当面コード上の `polaris` / `polaris-app` は内部コードネームとして残す。
